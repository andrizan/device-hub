# DirectDrive re-audit and implementation handoff (2026-11-15)

The first request is **P1: manage starting/stopping live lighting and restoring the lighting in the worker**. On top of that goes a layer of "firmware background + only the necessary keys lit by the PC". The existing depth, heatmap, key highlight, and ripple stay. This document supplements the [previous overall audit](AUDIT_HANDOFF.md) and the [live-lighting implementation and existing hardware records](LIVE_LIGHTING.md).

## Current state and the fixes made this time

- "Live" is shown through `LightArea::direct_drive` and `PerfCaps::live_travel`. The press depth goes HID worker → UI, the color computation is done by `livefx::Engine`, and sending goes UI → HID worker. It keeps running even after leaving the settings screen. In the demo, DirectDrive send/receive is a no-op, so the settings and screen behavior can be seen but the LED restoration cannot be verified.
- In the [XsyD driver](../crates/devhub-hid/src/xsyd.rs), colors are not written until the backup has succeeded for all chunks. A short read-back response or a mismatched chunk is also treated as a failure. If frame sending fails midway, the attempted cells are also tracked, and unconfirmed colors are not regarded as confirmed in the next diff decision.
- When a restore partly fails, the tracking and the original colors are kept and success is not returned. A stop failure is reported to the UI. Stopping an unused area sends nothing to HID. Re-reading the settings during live uses the saved-aside custom colors, not the temporary colors. When the app switches configurations, it first restores the original configuration and, if the restore fails, does not send the switch. While switching and re-reading, new DD frames are not accepted.
- Added "Stop live lighting" to the [command palette](../crates/device-hub/src/palette.rs), usable from another device or from Home. The traditional preview toggle is shown only when there is no read-back of the real-device colors, the selected area is DD-capable, and live lighting is not in use.

Verification: on Windows, `cargo test --locked --workspace` passed 53 tests (3 regression tests for communication failures added). `cargo clippy --locked --workspace --all-targets` succeeded, with warnings in 3 existing HID examples. `cargo build --locked -p device-hub` succeeded. In the SU66 Max demo, started live, moved to Home, stopped from the command palette, and returned to the Live tab to confirm "Stopped". This change was not verified by writing to a real device.

## Additional review (in priority order)

| Priority | Problem and basis | Owner / completion criteria |
| --- | --- | --- |
| **P1** | **The restore after stop and the job order cannot be guaranteed.** [`store::worker`](../crates/device-hub/src/store.rs) takes frames and control jobs from an unbounded queue, and `Shell::Drop` only sends a stop and waits 80 ms. If obtaining the lit colors or another HID command is slow, it does not get as far as the stop. The safety net in `XsydDriver::Drop` also waits for a response in `release_cells` → `cmd`. Together with the hardware record "the pins have no automatic timeout", restoration cannot be guaranteed after a forced termination. | **store / app**. Keep only the latest 1 frame, and discard the pending one on `Stop`. After a frame already being sent returns, stop before the next frame. Normal exit and backend switching handle stop completion or a deadline. Show "Restore again" on a restore failure. The stop ACK is the result of the host-side restore processing and is distinguished from the ACK of a DD frame. Verify delay, congestion, rapid clicks, exit, and restore failure → retry with a fake driver. |
| **P1** | **Owners get mixed up at start, reconnection, and on other paths.** [`fx_tick`](../crates/device-hub/src/pages/live.rs) waits while there is no session, but treats `dd_on=false` of the reconnected same ID as "stopped from outside". The session's `dd_on` is shared by the screen preview and live lighting, so a failure from an old `Msg::DirectDrive` can stop a display that has resumed. Configuration switching is protected when done through the app, but the case where the configuration is changed on the device itself is unverified. | **store / live**. Make the owner (screen preview / live) and the generation explicit. Do not hand over to the next owner until the restore succeeds. Make it possible to choose stopped by default or automatic resume on reconnection, and distinguish restoring, waiting, error, and the device being disconnected. Verify that an old result does not stop the current session, and that P1's saved-aside colors are not written to P2. |
| **P2** | **Read-back and the live stream consume the same HID worker.** Obtaining the lit colors on the Lighting screen takes at most 9 chunks. For depth acquisition, the UI is not told whether there is a new sample, and the UI's 33 ms cycle repeats the latest value. The heatmap is the number of observed threshold crossings and does not guarantee the physical total keystrokes. | **livefx / worker**. Move `armed/rearm` from `Engine` to the lifecycle side and run `measure → color calculation → DD` in the worker. Thin out delivery for the UI display. Do read-back only when the user is looking at the screen, at a low frequency depending on load. At minimum compare the number of HID reports for disabled / static hybrid / ripple / full refresh, frame delay p50/p95, stop time, and input interval. First measure stability at 30 Hz, and raise the rate only after measuring. |
| **P2** | **A cell left to the firmware cannot be distinguished from a cell lit black.** [`off_color`](../crates/device-hub/src/livefx.rs) decides the hybrid send targets by whether the color matches, so a highlight specified as black or a color rounded by low brightness is treated as transparent. Key highlight matches by the legend string, so the left and right of a split Space cannot be stored independently. | **livefx / UI**. In a frame, `None` leaves it to the firmware and `Some(Rgb::new(0,0,0))` means off. Store the user's selection with the layout's stable ID, and expand old labels when migrating. Test black, a highlight with the same color as the background, left and right Space, and old preset migration. |
| **P2** | **Reading custom lighting still has partial successes.** [`read_lighting`](../crates/devhub-hid/src/xsyd.rs) ignores per-key chunk failures, so blanks from a re-read or export may be treated as deletions by a later `write_per_key`. The Lighting screen also treats an empty real-device color map as not yet received, and falls back to the formula approximation when everything is off. | **HID / UI**. Represent "obtained empty set" and "not obtained" separately. On devices that support custom lighting, treat a partial read as a failure and keep the last confirmed values. Test all off, read unsupported, missing chunks, re-read and stop during DD, and base lighting changes separately. |

## Feature ideas (in implementation order)

1. **MVP: a game scene where only the necessary keys light up.** Example: with the firmware wave as the background, WASD fixed to blue, a short ripple only on the pressed movement keys, and the Caps Lock state at the top right. Color priority is "status display → press reaction → fixed keys → firmware background". First combine only fixed keys + ripple, and do the status display in the next stage. Save it in a "live scene" separate from the lighting settings, apply it from the preview, and do not persist it to the device. The stop common to all screens uses this time's palette.
2. **Show the state at hand with light.** Caps Lock / microphone mute / the existing mouse low-battery display, with selectable assignment targets. Provide a setting to show it briefly only when a threshold is crossed, and if the low-battery value is unknown, dismiss the display instead of specifying off. Make notification priority, low brightness, and no blinking configurable.
3. **Per-game scenes and sound effects.** Scene selection following app focus is an optional setting, and the target device is shown before always-on background execution or auto start. Music reaction is local processing using Windows output sound, processing only the signal of an explicitly chosen device. Scene editing works without focus linking or an audio source. Integration specific to external apps is a separate task.

Test a thin state machine (stopped / running / restoring / restore failed) and the latest-frame slot with a fake driver first. Keep the order of normal settings writes in the queue. 2. Finish the E2E for stop and configuration switching first. After adding counters for logging, move on to the `Engine` inside the worker. Do not grow the contract as long as it can be expressed with the existing `live_travel` / `direct_drive` / `direct_drive_stop`. If an addition is needed, the contract is additions only, and update the demo too.
3. Implement the MVP scene while keeping settings-file compatibility. Acceptance criteria: `None` and black are different, the firmware background continues for non-fixed keys, and stopping returns to the custom colors and firmware lighting from before the start.
4. Do hardware verification with the Web HUB and other HID clients closed, after exporting the configuration and lighting from before verification. Check in order: normal stop, window close, continuing while minimized, P1/P2 switching, unplug/replug. Do not force communication failures that tests can reproduce onto the real device. Record firmware restoration and stream stopping separately.
